# 기억산책 — 아이디어 분석 (웹앱 개발 착수 전)

작성 2026-11-12 · 기준 자료: 지원서(9/16), 융합팩토리 신청서·발표자료(3~4월), `08_기획고도화/기억산책_1R 기획방향_1109.md`, `07_제출서류/00_할일_타임라인.md`, 지역예선 평가지표(11/12)

## 1. 한 줄 정의 (현재 확정안, 11/9)

> 축제·관광지·전시 방문객이 **앱 설치 없이 QR**로 그 장소에 기억(감정·편지·사진)을 남기고, **디지털 엽서**와 **1년 뒤 회상 알림**을 받는 "장소 기억 캠페인" 서비스.
> 방문객은 무료, 돈은 참여·체류·재방문 성과가 필요한 **축제·지자체·관광 기관**이 캠페인 단위로 낸다.

## 2. 아이디어가 어떻게 바뀌어 왔나

| 시점 | 형태 | 고객 | 기술 | 바뀐 이유 |
|---|---|---|---|---|
| 1차 (모두의 창업 1차 / 융합팩토리, 3~4월) | 개인용 AR 기록 앱 | 개인 사용자 | iOS 네이티브 (SwiftUI·TCA·ARKit), 황리단길·영일대·구룡포 3곳 | — |
| 2차 지원서 (9월) | B2B2C 장소 기록 캠페인 | 로컬 공간·축제·문화행사 운영자 | **QR 모바일 웹**, 가벼운 AR 오브젝트 | 심사 의견: 지역 가치·지속 사용 동기·콘텐츠 제작 부담·수익모델 부족 |
| 1R 고도화 (11/9) | 축제·관광 캠페인 → 개인 아카이브 → 커뮤니티 3단계 | **축제·지자체·관광 기관 1순위**, 개별 소상공인 제외 | QR 웹 유지 | 콜드 스타트, 소상공인 지불 여력·운영 부담 |

**의미:** 웹앱으로 가는 건 이미 2차부터 정해진 방향이고, iOS 앱 구상(ARKit)은 2단계 "개인 아카이브 앱"으로 밀려났다. 지금 만들 웹앱은 **1단계 캠페인 도구**다.

## 3. 이해관계자별 가치

| 누구 | 겪는 문제 | 기억산책이 주는 것 | 돈을 내나 |
|---|---|---|---|
| 방문객 | 여행·축제의 감정은 사진첩·SNS에 흩어지고 금방 잊힘 | 1분 기록 → 예쁜 엽서 → 1년 뒤 "작년 오늘 여기서" 알림 | 기록은 무료. 실물 엽서·타임캡슐엔 소액 가능성 (2단계) |
| 축제·지자체·관광 기관 | 축제 끝나면 방문객과의 연결도 끝. 성과 보고는 입장객 수 위주 | ① 다음 해 축제 직전 재방문 알림 채널 ② 감정·체류 리포트(성과 보고 자료) ③ 방문객이 만든 홍보 콘텐츠 | **예 (1순위)** — 축제·관광 예산 |
| 문화시설·전시 | 관람객 참여 프로그램 필요 | 같은 구조의 캠페인 | 2순위 |

**핵심 판매 문장:** "1년 뒤 회상 알림 = 다음 해 축제 재방문 마케팅" — 기관이 돈을 내는 이유가 여기에 있다.

## 4. 사용자 흐름

```
[방문객]
QR 스캔 → 캠페인/스팟 페이지 → 감정 선택 → 편지·사진 작성 (AR 오브젝트 연출)
 → 공개 범위(전체/나만) → 회상 알림 받을 연락처 + 동의 → 디지털 엽서 발급(저장·공유)
 → … 1년 뒤 회상 알림 → 기억 열람 → 재방문 쿠폰 → 재방문

[운영자]
캠페인 생성 → 스팟·QR 발급 → 질문 템플릿·쿠폰 설정 → (축제 기간) 공개 기록 검수
 → 종료 후 자동 리포트 → 다음 해 축제 전 회상 알림 발송
```

## 5. 강점

1. **콜드 스타트를 잘 피했다.** 사람이 이미 모이는 축제에 붙으니 "빈 지도" 문제가 없다.
2. **방문객 진입 장벽이 낮다.** 앱 설치 없음, QR 한 번.
3. **돈 내는 사람과 이유가 분명하다.** 재방문 유도 + 성과 보고 자료는 공공 예산 집행 명분과 맞는다.
4. **실제 수요의 아날로그 근거가 있다.** 관광지마다 있는 "느린우체통"(1년 뒤 엽서 배달)이 같은 욕구의 오프라인 버전이다. 경쟁재이자 수요 증거이며, 사업계획서 차별성(Q1) 비교 대상으로 쓰기 좋다. *(실제 운영 현황은 번지 조사로 확인 필요)*
5. **1인 개발로 만들 수 있는 범위다.** 기획·개발 역량이 있고(ADA 수료, 앱 5종·웹 4종) 핵심 흐름이 단순하다.

## 6. 약점·리스크 — 웹앱 설계에 직접 영향을 주는 것

### 6-1. "1년 뒤 알림"을 웹에서 어떻게 보낼까 (가장 중요)
- 설치 없는 웹앱이라 **웹 푸시는 사실상 못 쓴다.** iOS Safari는 홈 화면에 추가한 PWA에서만 웹 푸시를 지원하는데, 축제 방문객이 그걸 할 리 없다.
- 남는 채널은 **이메일 / SMS / 카카오 알림톡**. 결국 **연락처를 받아야** 하고, 이게 기록 완료율을 떨어뜨리는 가장 큰 마찰이 된다.
- 알림톡은 카카오 비즈니스 채널(보통 사업자 필요)이 있어야 해서 예비창업 단계에서는 바로 쓰기 어려울 수 있다 → **MVP는 이메일 + (선택) SMS**로 시작하고, 알림톡은 사업자 등록 뒤에 붙이는 게 현실적이다.
- 연락처를 1년 넘게 보관해야 하므로 **보유기간을 명시한 개인정보 동의**가 필요하다.
- **설계 제안:** 연락처는 기록을 마친 뒤 "엽서 받기/1년 뒤 받기" 단계에서 **선택 입력**으로 받는다. 기록 완료율과 알림 등록률을 별도 지표로 본다.

### 6-2. 회상 시점은 "365일 뒤"보다 "다음 해 축제 직전"
- 운영자 가치(재방문)를 생각하면 기계적인 1년보다 **다음 회차 개최 1~2주 전**에 보내는 게 맞다. 캠페인에 "회상 발송일"을 운영자가 정하게 하면 된다.
- 기본값은 "작년 오늘"(감성), 운영자가 바꿀 수 있게(재방문) — 두 가치를 모두 살린다.

### 6-3. 1년짜리 효과는 실증 기간 안에 증명할 수 없다
- 4주 실증이나 2R 평가 기간 안에 "1년 뒤 재방문"은 측정이 불가능하다.
- **대리 지표:** 알림 등록률(연락처 남긴 비율), 엽서 저장·공유율, 기록 재열람률, 운영자 지불의사.
- 데모용으로 **"회상 미리보기 / 지금 발송" 버튼**을 운영자 화면에 두면 시연이 된다 (타임라인의 "회상 알림은 화면·예약 데모"와 일치).

### 6-4. 웹 AR의 한계
- iOS Safari는 WebXR을 지원하지 않는다. 진짜 공간 고정 AR은 웹에서 어렵거나 유료 SDK가 필요하다.
- 기획 문서도 "AR은 연출 요소"로 정리했으니, **카메라 화면 위에 감정 오브젝트를 띄우는 오버레이**(getUserMedia + CSS/Canvas 애니메이션)면 충분하다. 카메라 권한을 거부하면 일러스트 배경으로 대체한다.
- 권한 팝업 자체가 이탈 요인이다 → AR은 **기록 후 엽서 연출**이나 선택 단계로 두고, 핵심 흐름에 넣지 않는 걸 권장한다.

### 6-5. 위치정보
- QR이 곧 장소 인증이므로 **GPS를 수집하지 않으면** 위치정보법 부담이 크게 줄어든다(스팟 ID만 저장). 그래도 멘토·전문가 확인은 필요하다(기획 문서 리스크 항목).

### 6-6. 공개 기록 관리
- 전체 공개 기록은 욕설·광고 위험이 있다 → **운영자 검수 큐 + 신고 + 금칙어 필터**. 축제 기간에만 운영하니 부담은 제한적이다.

### 6-7. 아직 근거 없는 것
- **캠페인 가격**: 근거 없음(기획 문서에 명시). 담당자 인터뷰로 가설을 세워야 한다.
- **방문객이 실제로 1분을 쓸지**: 랜딩 사전신청과 지인 테스트로 확인해야 한다.
- AI 가상설문(비즈포지)은 가설용으로만 쓴다.

## 7. 웹앱 MVP 범위 제안

### 7-1. 11/19까지 (보고서·평가용 시제품) — 꼭 동작해야 하는 것
타임라인 기준: 프로토타입은 11/13 범위 확정 → 11/19 완성·지인 테스트 → 11/23 보고서에 캡처.

| # | 화면 | 설명 |
|---|---|---|
| 1 | 스팟 진입 (`/c/{campaign}/s/{spot}`) | QR 랜딩. 축제·장소 이름, "여기에 오늘의 기억을 남겨보세요" |
| 2 | 감정 선택 | 감정 오브젝트 5~6종 (기쁨·설렘·평온·그리움·감사 등) |
| 3 | 기억 작성 | 짧은 편지(글자 수 제한) + 사진 1장(선택) |
| 4 | 공개 범위 | 전체 공개 / 나만 보기 |
| 5 | 엽서 받기 | 장소·날짜·감정·문구가 합쳐진 엽서 이미지 생성, 저장·공유 |
| 6 | 1년 뒤 받기 | 이메일(선택) + 개인정보 동의 → "○○년 ○월에 이 기억이 열립니다" |
| 7 | 회상 열람 (`/m/{token}`) | 알림 링크로 여는 페이지. 그때의 기억 + 재방문 쿠폰 |
| 8 | 운영자 데모 화면 | 캠페인 수치(진입·기록·완료율·감정 분포) + "회상 알림 지금 발송" 버튼 |

### 7-2. 실증 전까지 (2R 이후)
- 운영자 콘솔: 캠페인·스팟 CRUD, QR 일괄 발급(인쇄용 PDF), 질문 템플릿, 쿠폰
- 공개 기억 벽 (스팟별 공개 기록 모아보기)
- 검수 큐·신고
- 자동 리포트 (PDF/웹): 참여 수, 완료율, 감정 분포, 시간대별 참여, 대표 기록, 알림 등록률
- 회상 알림 예약 발송 (스케줄러) + 쿠폰 사용 체크
- 카메라 오버레이 AR 연출

### 7-3. 나중에 (2·3단계)
개인 아카이브(내 기억 지도), 친구 공개, 실물 엽서 결제, 네이티브 앱 + ARKit, 커뮤니티·구독, 동의 기반 인사이트

### 7-4. 데이터 모델 초안

```
Organization (기관)        id, name, contact
Campaign (캠페인)          id, org_id, name, starts_at, ends_at, recall_at(회상 발송일), theme, status
Spot (스팟 = QR 1개)       id, campaign_id, name, description, image, slug
Memory (기억)              id, spot_id, emotion, text, photo_url, visibility(public|private),
                           moderation_status, created_at, view_token
RecallSubscription         id, memory_id, channel(email|sms), address, consent_at, send_at, sent_at, opened_at
Coupon / Redemption        id, campaign_id, title, terms / coupon_id, memory_id, redeemed_at
Event (지표용)             spot_id, type(enter|start|complete|postcard_save|share|recall_open), at
```
- 방문객 계정 없이 **기억마다 비밀 토큰 링크**로 소유권을 처리한다 (설치·로그인 없음 원칙).
- Event 테이블 하나로 리포트·완료율·퍼널을 모두 계산한다.

### 7-5. 기술 선택 시 고려할 점 (확정 아님)
- **모바일 웹 우선**, 첫 화면이 3G에서도 빨라야 한다 (축제 현장은 통신이 혼잡하다).
- 엽서 이미지는 서버에서 생성해야(OG 이미지 방식) 카톡 공유 미리보기에도 그대로 쓸 수 있다.
- 사진 업로드는 클라이언트에서 리사이즈한 뒤 올린다.
- 예약 발송에는 크론/스케줄러가 필요하다 → 서버리스라도 스케줄 작업을 지원하는 곳.
- 1인 개발과 1주 일정이면 **인증·DB·스토리지가 한 번에 되는 BaaS + 풀스택 프레임워크** 조합이 유리하다. 구체적 스택은 개발 착수 시 정한다.

## 9. 결정이 필요한 질문

1. **회상 전까지 기억을 봉인할까?** 엽서는 즉시 주되 편지 원문은 1년 뒤에만 열리게 하면(타임캡슐) 기대감은 커지지만, 지금 다시 보고 싶은 사람은 불편하다.
2. **알림 채널:** 이메일만으로 시작할지, SMS까지 할지 (비용·사업자 여부).
3. **11/19 데모의 기준 장소:** 실제 축제(포항 등 겨울 행사)로 할지, 영일대 같은 상설 관광지로 할지.
4. **AR 연출을 데모에 넣을지:** 일정상 엽서 연출 수준으로만 할지.
5. **랜딩(핸디핏)과 웹앱의 관계:** 랜딩은 핸디핏으로 따로 두고 웹앱은 시제품 전용으로 할지, 웹앱 안에 랜딩까지 넣을지.
